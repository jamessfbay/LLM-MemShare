# Multi-tenant isolation: implementation design

Status: target policy and production release requirements. Parts are implemented in the Rust alpha; this document is not a claim that every requirement below is complete. The [architecture](ARCHITECTURE.md), [API](API.md), and [security boundaries](SECURITY.md) describe current behavior. This document refines [the implementation plan](IMPLEMENTATION_PLAN.md).

Current gaps include owner-agent disablement cascades, comprehensive grant revocation during offboarding, run credentials, proposal/review and export paths, administrative hard deletion, audit-reader controls, denial auditing, and complete policy-matrix tests. The current handoff API reports omitted-reference counts, while section 5 proposes a stricter boolean-only indicator. Current handoff cursors encode `(created_at,id)` and reauthorize each page; they are not signed or bound to filters. These target changes require implementation and tests before they can be claimed as guarantees.

## 1. Boundary and guarantees

A tenant is the isolation boundary in a shared application and PostgreSQL deployment. All tenant-owned content and metadata, including derived copies and operational records, is tenant scoped. No API supports cross-tenant resource access. The authenticated principal, not a request parameter, determines the tenant. Every request and job is denied by default if identity, tenant context, membership, or applicable authorization cannot be verified. Authorization precedes content access and response serialization.

Production claims require all release gates in section 11 and an independent security review. The design protects against ordinary application authorization defects in addition to intentional untrusted clients, but shared application compromise, arbitrary SQL execution under the runtime identity, privileged database compromise, or host/backup compromise can cross tenant boundaries. RLS with a mutable session variable is a defense against missing tenant predicates, not isolation from arbitrary SQL or a malicious runtime. Deployments requiring containment of a compromised application process need separate credentials/processes and databases or stronger isolation, designed and tested separately.

Excluded: cross-tenant sharing, anonymous tenant access, automatic content transfer to external providers, and administrator access to private content. Availability and resource isolation need quotas and capacity controls; RLS alone does not prevent noisy neighbors.

## 2. Identity, lifecycle and policy

Identifiers are opaque, immutable UUIDs generated by the server. A tenant owns workspaces and principals. A project belongs to one workspace. Principals are tenant-scoped users, services and agents; identities that represent the same person in different tenants are separate. A principal has active or disabled status. Every credential has an ID, principal, tenant, verifier, creation, optional expiry, revocation and last-used metadata. Credentials are random and shown only once; do not log them. Tenant and workspace selection from a client are selectors only and must be checked against the authenticated identity and membership.

Tenant administrator, workspace administrator, member, and project roles are explicit membership assignments. Administration of membership and grants does not confer private-content access. Owners of private resources can read, write, delete, and grant permitted access; tenant policies can restrict these actions. Services and agents require an explicit grant plus active workspace membership. A shared workspace/project resource is owned by that workspace/project; its roles determine content access. A tenant administrator may administer a workspace only when assigned its administrator role. Tenant administrators cannot read or transfer private content merely by virtue of their role.

Initial role defaults, subject to tenant policy restrictions (never implicit cross-tenant access):

| Scope | Actor | Read/list | Create/update | Delete | Grant/revoke | Approve promotion |
| --- | --- | --- | --- | --- | --- | --- |
| Private | Active owner | Yes | Yes | Yes | Yes, within owned resource | Yes for owned source and authorized target |
| Private | Other user, service or agent | Explicit action grant | Explicit action grant | Explicit action grant | No | No |
| Workspace | Active workspace admin | Yes | Yes | Yes | Yes for workspace scope | Yes if source readable and target writable |
| Workspace | Active member | Yes | Yes for records they create | Own records | No | No |
| Project | Project admin | Yes | Yes | Yes | Yes for project scope | Yes if source readable and target writable |
| Project | Project member | Yes | Yes for records they create | Own records | No | No |
| Any | Tenant admin without applicable scope role/grant | No | No | No | No content grant | No |
| Any | Disabled, removed or revoked principal | No | No | No | No | No |

Read/list includes search, context, handoff references and exports. Create requires active workspace membership; project access requires project membership as well. Workspace/project users may receive explicitly narrower policy, but deny overrides an allow. Services and agents have no ambient role-based content access and need explicit action grants even when members. An agent must have an active owning user or service; a user's removal disables dependent agent credentials. The initial implementation forbids grant delegation by grantees and forbids grants to another tenant. Owner, workspace admin or project admin may issue only grants within their scope and maximum authority. A grant has explicit subject, resource or scope, actions, issuer and expiry (a deployment policy sets a maximum lifetime); revoke by grant ID. All administration changes are auditable.

Scratch data is bound to a server-created run, an agent and workspace, with required expiry. A short-lived run credential binds tenant, principal and run and cannot access another run. Owner access and promotion must use explicit grants and source-version approval. If trusted run issuance is absent, disable agent scratch entirely.

Removing a member atomically disables applicable memberships, grants and dependent agent credentials; operations newly authorized after commit fail. Existing private content remains under its existing owner, inaccessible until the owner is restored or an explicitly approved recovery workflow is implemented. No administrator-readable transfer is silently implied. Account deletion and tenant deletion use auditable, separately authorized workflows with retention/hold checks; do not offer ownership transfer in the alpha without explicit consent or a reviewed recovery mechanism.

## 3. Data model and constraints

Use tenant-scoped composite keys and foreign keys rather than relying on opaque IDs alone. Exact physical types and indexes are migration deliverables; these constraints are mandatory:

| Relation | Required identity and constraints |
| --- | --- |
| tenants | `tenant_id` primary key, status and lifecycle timestamps. |
| principals | `(tenant_id, principal_id)` primary key; kind, status and optional owner principal with same-tenant foreign key. |
| credentials | Credential ID, globally unique token verifier, tenant and principal composite foreign key; status, expiry and revocation. Authentication lookup is a separate controlled path. |
| workspaces/projects | `(tenant_id, workspace_id)` and `(tenant_id, workspace_id, project_id)` keys; project foreign key to workspace. |
| memberships | Tenant, workspace/project and principal composite foreign keys; role and status; uniqueness for active assignments. |
| grants | Tenant, subject, issuer, workspace, target type/ID, actions, expiry and revocation; validate target's tenant and scope. Prefer typed target relations/foreign keys over unchecked polymorphic IDs. |
| memories | `(tenant_id, memory_id)` primary key, workspace, optional project, scope, owner, creator, type, content, version, expiry and deletion state; same-tenant composite foreign keys and scope/owner consistency checks. |
| memory_versions, proposals, handoff_references | Tenant and parent ID with composite foreign keys; references must remain in the same tenant and workspace unless policy explicitly permits otherwise. Historical content inherits the parent resource's access rules. |
| idempotency | Unique `(tenant_id, principal_id, operation, key)` plus canonical input hash, result identifier and expiry; no response content. |
| audit_events | Tenant, actor, action, outcome, request ID, target identifier and time; no payload or credential. Restrict audit readership separately. |
| runs and outbox | Tenant and parent composite foreign keys; jobs contain identifiers rather than unrestricted content. Outbox is introduced with asynchronous indexing. |

Use uniqueness, checks and foreign keys for tenant consistency and valid states. Explicitly model shared versus private ownership rather than making a single user owner stand for a workspace. Database constraints can reveal existence through errors; API responses normalize such failures and never return raw SQL errors. Use indexes beginning with tenant and access/filter fields for hot queries. Define page cursors with stable `(updated_at, id)` ordering and bind signed or opaque cursor state to tenant, principal, filters and expiry; verify authorization on every page.

## 4. Authentication and database access

The bootstrap/control-plane path uses a separate tightly scoped operational identity, not the ordinary tenant data role. Provisioning requires an authenticated deployment operator; create a tenant and its first administrator atomically and record an administrative audit event. There is no unauthenticated tenant creation. Operator credentials, recovery and tenant suspension are documented and exercised. Once provisioned, tenant administration is tenant-scoped.

For ordinary authentication, the Rust service hashes the presented high-entropy token with SHA-256 and resolves it through a narrowly privileged SQLx query that returns only credential ID, tenant ID, principal ID, status and expiry. This is a pre-tenant operation: isolate its table or expose a reviewed, fixed `SECURITY DEFINER` function with a fixed safe `search_path`, schema-qualified names, restricted `EXECUTE`, no dynamic SQL, no public access and no content access. Avoid functions if a narrowly privileged dedicated lookup role is sufficient. Never let the caller choose returned identity. Verify credential and principal status and tenant status before opening the tenant transaction. Prevent raw database errors from reaching clients. Test malformed credentials, revoked and expired credentials and tenant suspension.

Database roles: a non-login schema owner; a separately controlled migration role; an application runtime role with only necessary DML, `NOBYPASSRLS`, no ownership, superuser, role switching to privileged identities, schema creation or `TRUNCATE`; a tightly scoped authentication lookup role; and separate operational backup/migration identities. Audit and workers receive only required privileges. RLS applies to every tenant-owned table including versions, grants, membership, idempotency, audit, jobs and derived tables. Enable and force RLS for table owners where applicable, and test policies for SELECT, INSERT, UPDATE and DELETE, including `WITH CHECK`. Superusers and `BYPASSRLS` roles bypass RLS; no application role may have these attributes. Default-deny applies when context is missing or invalid.

After authentication, acquire a connection, start a transaction, set validated tenant context transaction-locally using parameterized `set_config(..., true)`, perform authorization and all resource queries on that connection, then commit or rollback before returning it to the pool. Do not use session-level tenant state. Fail closed on context setup failure. Reset/discard contaminated connections after transaction errors. Test commit, rollback, exceptions, connection reuse, concurrent tenants and supported pool modes. Transaction pooling is supported only if the complete transaction stays on one backend; statement pooling is unsupported for this design.

RLS policies compare each row's tenant ID with the transaction context, including both `USING` and `WITH CHECK`; application policy additionally checks principal, membership and resource action. The runtime role can set a custom setting, so SQL injection or a compromised runtime can alter tenant context. Prevent injection with parameterized SQL and input validation, and do not treat the setting as a cryptographic identity. Test direct context manipulation to demonstrate this limitation; choose stronger database-per-tenant isolation when that threat is in scope. Review views, functions, partitions, maintenance jobs and policy composition for bypasses. No blanket permissive policy may weaken the tenant predicate.

References: [PostgreSQL row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html), [role attributes](https://www.postgresql.org/docs/current/role-attributes.html), and [configuration setting functions](https://www.postgresql.org/docs/current/functions-admin.html).

## 5. Request, authorization and concurrency

Each request: (1) authenticate and resolve active principal/tenant, (2) begin a tenant-scoped transaction, (3) validate active membership and credential status against authoritative state, (4) authorize the action and resource within tenant/workspace, (5) perform the operation and append audit metadata, (6) commit, and (7) serialize only authorized fields. Do not trust data returned by another adapter or index without this path. Search applies access filtering before limits; references and exports are reauthorized. No cached authorization decision may outlive revocation semantics.

Use READ COMMITTED and a fresh authorization statement after entering the transaction. Revocation must commit before the fresh authorization statement's snapshot begins for the new request to be denied. An already authorized in-flight operation may finish; define authorization's linearization point as that statement. Do not reuse a long-lived snapshot or cache for this decision. If a single operation spans multiple transactions, each data-returning transaction reauthorizes. Test with two database connections and synchronization barriers, not sleeps.

Approval locks the proposal and source in one documented order; version check and creation of the promoted record occur in the same transaction. An update committed before the source lock yields a conflict; one ordered after approval may succeed. Resolve deadlocks by transaction retry with bounded attempts and idempotent effects. Create and handoff retries use tenant/principal/operation-scoped idempotency keys, request hash and result ID; reauthorize on replay. A different request returns 409; unavailable results use the same externally visible response as an inaccessible resource. Retention and key reuse must be published in the API contract.

For a handoff, reject creation when any reference is inaccessible; at read/export return the handoff with inaccessible references omitted and a generic `references_omitted: true`, without identifiers or counts. Reauthorize each reference against the current principal. Handoff text may itself contain sensitive data; reference checks cannot sanitize copied text. Never accept arbitrary client-provided verified provenance.

## 6. Migration and rollout

1. Inventory the existing schema, credentials, memories, histories, grants, proposals, idempotency and audit; back up and test restore in an isolated environment. Freeze writes during cutover. Never run the migration against an unreviewed database.
2. Require an operator-supplied mapping for every legacy tenant/workspace/user/agent and scope. Validate uniqueness, orphan references, expiry, ownership, source, conflicts and grants. Produce a dry-run manifest with counts and rejected records without printing memory content or credentials. Fail closed on ambiguity; organization/project labels remain private unless explicitly remapped with owner authorization.
3. Apply versioned schema and data migrations under a controlled migration role. Backfill tenant IDs into all child relations, validate composite foreign keys and constraints, then enable and force RLS. Disable legacy credentials and issue new ones via the secure provisioning flow; do not expose old tokens. Rebuild idempotency state or explicitly invalidate it with documented client impact.
4. Verify counts, checksums where appropriate, constraints and tenant-specific queries with the runtime role. Execute cross-tenant denial tests, role privilege checks and the two-tenant journey against a restored production-like fixture. Obtain operator sign-off before routing traffic. Monitor authentication, denial and migration errors without logging content.
5. If cutover fails before accepting new writes, restore the verified backup and previous application version. After accepting writes, do not roll back to a backup blindly: stop writes and use a tested forward repair or a separately designed reconciliation/export procedure. Document the recovery point and data-loss window; retain backup per policy and apply deletion replay on restore.

## 7. Operations, retention and incident handling

Use TLS at ingress and authenticated, encrypted database connections where traffic crosses a trust boundary. Run non-root containers with isolated secrets and least-privilege network access. Configure per-tenant request, storage, concurrency and job quotas; apply bounded request sizes and timeouts. Tenant suspension disables authentication and jobs, and does not by itself erase data. Default metrics must not include content, credentials or high-cardinality tenant IDs as labels; controlled audit logs may contain tenant and actor IDs with documented retention.

Define backup encryption, access, rotation, retention, restore testing and legal-hold behavior per deployment. Hard deletion removes authorized content and historical/derived copies from live storage; append a minimal deletion tombstone without content so recovery can replay deletion after restoring a backup. Tombstones themselves need retention and access controls. Report backup expiry separately from live deletion. An immutable external audit sink, if used, has its own policy and evidence; application insert-only behavior alone is not tamper proof.

Incident runbooks cover disabling a tenant or credential, isolating a deployment, collecting restricted audit evidence, rotating credentials, restore and notification decisions. Treat a suspected runtime or database privileged compromise as potentially affecting all tenants of the shared deployment; do not promise containment that this architecture cannot provide.

## 9. Verification matrix

| Area | Required cases and evidence |
| --- | --- |
| Identity | Invalid, expired, revoked and disabled credentials; suspended tenant; duplicate issuance; pre-tenant lookup cannot read content. |
| Isolation | Two tenants with deliberately overlapping external names; ID guessing on every read/write/list/search/context/export/review/grant route; no existence leakage. |
| Within tenant | Every matrix cell for each action and scope; owner, member, admin, explicit grant, agent and removed principal; both allow and deny. |
| RLS and roles | Missing/invalid tenant context, wrong tenant, all DML including `WITH CHECK`, non-owner role, owner/FORCE behavior, roles without BYPASSRLS, catalog coverage and privileged role separation. |
| Pool and transactions | A then B on same connection after commit, rollback, exception and cancellation; parallel tenants; no context bleed. |
| Concurrency | Revocation before/after authorization snapshot; update before/after review lock; retries, conflicts and deadlocks with deterministic barriers. |
| References and retry | Cross-tenant and revoked references on create/read/export; omitted reference response; idempotency collision, expiry, retry after revoke/delete and no content snapshots. |
| Lifecycle | User/agent disablement, membership removal, tenant suspension, scratch expiry, retention, hard deletion, backup restore and deletion replay. |
| Migration | Empty install, mapped prototype data, ambiguous/orphaned rows fail closed, RLS enabled after cutover, recovery before and after writes. |
| Derived systems | Stale index, asynchronous retry, deletion/revocation propagation and authorized recheck before content return. |
| Observability | Audit actor/tenant/outcome accuracy, denied requests, log redaction, and audit reader authorization. |

Every API route and database relation must be mapped to at least one test in a maintained coverage inventory. CI reports executed, passed, failed and skipped counts; required security tests cannot be skipped. Use real PostgreSQL and runtime roles for integration tests, not mocks alone. Test fixtures contain no production secrets.

## 10. Open decisions

Before implementation approval, document tenant-specific role customization, maximum grant lifetime, retention and legal hold defaults, admin recovery/ownership transfer, provisioning and identity-provider integration, audit retention, quota values and which deployment isolation class is supported. Until decided, keep the capability disabled or use the restrictive default above. A production deployment must provide concrete settings and accountable operational owners; this document is not proof those decisions have been made.

## 11. Production isolation release gates

- [ ] Reviewed threat model, complete policy matrix and explicit supported deployment/isolation class.
- [ ] All tenant-owned tables and routes inventoried; runtime privilege, RLS and composite constraint audits pass.
- [ ] All required section 9 tests pass in CI and on a production-like deployment; no skipped security tests or open cross-tenant leak.
- [ ] Migration, backup/restore, deletion replay and incident exercises have dated evidence and named owners.
- [ ] TLS, credential lifecycle, quotas, logging/redaction, monitoring, secrets and backup policies are configured and verified.
- [ ] Independent security review is complete, findings are triaged and blocking findings remediated; release owner approves residual risk.
- [ ] API, operational documentation and release notes state guarantees, in-flight revocation behavior, limitations and supported versions.

These are acceptance criteria for implementation and operations, not claims that the current prototype meets them.
